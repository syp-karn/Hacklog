## Command Injection Vulnerability

Inspecting [`server.py`](http://server.py) closely, we can see this line:-

```python
subprocess.Popen(f"echo 'Archive: {job_name}' >> /tmp/archive.log", shell=True)
```

User input (`job_name`) is directly inserted into a shell command by the service, and then executed to create logs. This looks like a potential command injection vulnerability!

I tried many different `netcat` and `curl` requests, to confirm the command injection, and also many reverse shell payloads, but non received a connect back from the machine.

Finally, tried this payload:-

```bash

        self._address = address

    def get_line(self):
        """Reads until a newline to get a single PJL command."""
        line = b""
        while True:
            char = self._client.recv(1)
            if not char: return None
            line += char
            if char == b"\n": break
        return line

        if isinstance(message, str):
            message = message.encode("utf-8")
        self._client.sendall(message)

        return os.path.normpath(os.path.join(self._root, clean))
```

### root through `paperwork-daemon`

The daemon opens a sensitive configuration file as root when it starts:

`admin_fd = os.open("/etc/paperwork/admin_pins.conf", os.O_RDONLY)`

The daemon opens `/etc/paperwork/admin_pins.conf` as root and monitors:

```
/home/archivist/printer/logs/commands.log
```

If the log contains `FSQUERY`, `FSUPLOAD`, or `FSDOWNLOAD`, it enters a lockdown routine and sends two file descriptors to the connected client using `SCM_RIGHTS`.

Since `archivist` owned `/run/paperwork/mgmt.sock`, I triggered the condition by sending a PJL `FSQUERY` command to the local printer service, then connected to the management socket and received the file descriptors.

The second descriptor provided the contents of:

`/etc/paperwork/admin_pins.conf` which contained the password:-

`ADMIN_PASSWORD=ApparelMortuaryCedar22` 

Tried using the password to `su` to root.

# Learnings

- `subprocess.Popen(cmd, shell=True)` inherits whatever `/bin/sh` is on that box, and `sh` is frequently *not* bash and lacks bash-only features (`/dev/tcp`, arrays, `[[`, process substitution, etc). Anything relying on a bash-specific mechanism needs an explicit `bash -c` wrapper to guarantee it's actually bash parsing the string, regardless of what the system's default shell symlink points to.
